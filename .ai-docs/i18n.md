# i18n — typed dictionary, interpolation, plurals

Two locales, both bundled statically: `zh-CN` and `en-US`. There is no vue-i18n.

| File | Role |
| --- | --- |
| `src/i18n/index.ts` | `TranslationSchema` — the **source of truth for keys**. `useI18n()` lives here too. |
| `src/i18n/locales/zh-CN.ts` / `en-US.ts` | The messages, typed as `TranslationSchema` so a missing or misspelled key is a compile error. |
| `src/i18n/format.ts` | Pure `formatMessage` / `formatPlural` — the message syntax. Unit-tested by `tests/i18n-format.test.mts`. |
| `src/stores/locale.ts` | `current` locale (persisted via `ConfigService.SaveConfigField('language', …)`), `t`, `tf`. |

## Two accessors, one rule

```ts
const { t, tf } = useI18n()
```

- **`t['key']`** — the raw dictionary. No parameters, no formatting, zero cost. This is the default.
- **`tf('key', params)`** — translate *and* format. Use it whenever the message has `{placeholders}`;
  pass a **number** instead of an object to pick a `singular | plural` branch.

```vue
{{ t['sidebar.inbox'] }}
{{ tf('sidebar.unread', { count: store.accountUnread(id) }) }}
{{ tf('mail.remote.blocked_short', props.count) }}   <!-- plural, count in one argument -->
```

Both stay reactive: `tf` is a plain function that reads the store's `current` ref on every call, so any
render or `computed` that calls it re-runs when the language changes.

## Message syntax (a subset of vue-i18n's)

**Named interpolation.** `{count}`, `{email}`, `{user-name}` (letters/underscore first, then
letters/digits/`_`/`-`). A placeholder with no matching parameter is left standing rather than blanked,
so a typo shows up in the UI as `{emial}` instead of silently disappearing.

**Pluralisation.** `singular | plural`, chosen by `Intl.PluralRules` for the active locale. `count` is
both the selector and an implicit `{count}` / `{n}` parameter; pass either in `params` to override the
printed value.

```ts
'mail.remote.blocked_short': 'Blocked {count} remote resource | Blocked {count} remote resources',  // en
'mail.remote.blocked_short': '已拦截 {count} 个远程资源',                                            // zh — one branch
```

- Chinese has no plural forms, so it writes **one** branch, which is always used.
- A language needing more than two forms lists them in `Intl.PluralRules` order:
  `zero | one | two | few | many | other`.
- Duplicating a long sentence across branches is normal and expected (that is how plural messages
  work everywhere) — `mail.cssArt.blocked` does it.
- A pluralised message cannot contain a literal `|`.

## Rules

- **Never `.replace()` a translated string.** `String.replace` also treats `$&`, `$1` in the
  *replacement* as patterns, so a value containing `$` corrupts the output — that is why `formatMessage`
  uses a replacer function. `tests/i18n-format.test.mts` pins this down.
- **Never build a sentence from fragments.** `t['x'] + '?'` and `` `${t['a']} ${name}` `` break as soon
  as word order or punctuation differs (Chinese wants `删除？`, not `删除?`). Put the variable part in
  the message: `tf('settings.llm.delete_model', { model })`, `tf('busy.seconds', { label, s })`.
- **A new key goes in three files**: `index.ts` (schema), `zh-CN.ts`, `en-US.ts`. `typecheck` catches
  a missing one.
- **The unit belongs to the message, not the label.** `BusyButton` used to glue `{s}s` onto its label,
  which rendered 「打开浏览器授权 06s」 in Chinese; the pattern is now `'busy.seconds'`
  (`'{label} {s}s'` / `'{label} {s} 秒'`).

## Why not vue-i18n

The guide's *Syntax* and *Pluralization* chapters were the reason to look at it, and the two features
worth having are exactly `{name}` interpolation and `one | other` branches — `format.ts` implements
those, with the same syntax, in ~70 lines. Adopting the library would mean:

- rewriting 200+ `t['key']` call sites into `t('key')` (or re-deriving the typed-key safety that the
  flat dictionary already gives us for free);
- pulling in the message compiler for a 2-locale, statically-bundled app — no lazy loading, no locale
  fallback chain, no `n()`/`d()` number-and-date formatting anywhere in the codebase;
- a second source of truth for keys (vue-i18n's `DefineLocaleMessage` vs. our `TranslationSchema`).

If a future requirement lands that this genuinely cannot serve (per-locale date/number formats,
lazy-loaded locales, ICU select/plural-with-offset), migrate then: the message files are already in
vue-i18n's syntax, so they carry over unchanged.

## Checking a locale change

```bash
cd frontend
pnpm test        # includes tests/i18n-format.test.mts
pnpm typecheck   # a key present in one locale but not the schema fails here
```
